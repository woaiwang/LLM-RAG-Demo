## 三、实验过程与遇到的问题

### 3.1 环境配置

- **Python环境**: conda `ultrarag` 环境（位于 `C:\Users\zzy\miniconda3\envs\ultrarag`）
- **LLM**: DeepSeek API (`deepseek-chat` 模型)
- **Embedding**: BAAI/bge-small-zh-v1.5
- **Reranker**: BAAI/bge-reranker-base (Cross-Encoder)

### 3.2 问题1：PDF上传时文件名中的中文引号导致文件找不到

**现象**: 上传5份PDF时，"附件1：东大团发〔2026〕3号：关于开展东北大学2026年"五四奖章""五四奖状"评选的通知.pdf" 这个文件的 `os.path.exists()` 返回 False。原因是 Python 源码中硬编码的文件名字符串使用了 ASCII 直引号，而实际文件名使用的是 Unicode 弯引号（Smart Quotes），两者不匹配。

**解决方法**: 改用 `os.listdir()` 动态遍历目录匹配文件名，而非硬编码字符串列表。见 `tmp_upload_pdfs.py`。

**教训**: 处理含中文特殊字符的文件名时，始终用 `os.listdir()` 动态匹配。

### 3.3 问题2：Windows终端GBK编码不支持emoji打印

**现象**: Python 脚本中使用 `✅` `❌` `⚠️` 等 emoji 字符进行日志输出时，conda 环境的 Windows 终端报 `UnicodeEncodeError: 'gbk' codec can't encode character`。

**解决方法**: 将所有 emoji 替换为纯文本标记（如 `[OK]` `[FAIL]`）。

### 3.4 问题3：eval_dataset.jsonl 中 source_doc 匹配失败

**现象**: 运行评估时，`source_doc: "推免"` 始终无法匹配到任何检索结果。追踪后发现原因：实际文件名是 "计算机科学与工程学院2023年推荐优秀应届本科毕业生免试攻读研究生遴选实施细则.pdf"，包含"推荐"和"免试"但**不包含连续子串"推免"**。而评估器的匹配逻辑是 `source_doc in filename` 的子串检查。

**解决方法**: 将 `eval_dataset.jsonl` 中所有 `"source_doc":"推免"` 替换为 `"source_doc":"免试攻读"`。

**验证**: 编写脚本逐题验证所有 source_doc 是否能匹配到至少一个文件名，确认全部30题通过。

**教训**: 测试数据中的 source_doc 必须使用文件名中实际出现的连续子串。

### 3.5 问题4：Reranker 首次加载耗时较长

**现象**: 配置6（Hybrid+Reranker）首次运行时，`sentence_transformers.CrossEncoder` 需要从 HuggingFace 下载 BAAI/bge-reranker-base 模型（约1.1GB），导致首条查询延迟高达6.45秒。后续查询因模型已缓存，延迟降至约2-3秒。

**解决方法**: 这是正常行为，首次加载不可避免。已通过模块级全局变量 `_reranker_model` 实现懒加载 + 缓存，后续调用不再重复加载。

### 3.6 问题5：conda run 不支持多行 Python 脚本

**现象**: 尝试用 `conda run -n ultrarag python -c "..."` 传递多行脚本时，conda 报错 `AssertionError: Support for scripts where arguments contain newlines not implemented`。

**解决方法**: 将 Python 脚本写入临时文件（如 `/tmp/script.py`），然后用 `conda activate + python script.py` 的方式执行：
```bash
. "C:/Users/zzy/miniconda3/etc/profile.d/conda.sh" && conda activate ultrarag && python script.py
```

## 六、深度分析

### 6.1 按类别分析

#### A类-精准事实查询（HR@3 = 83.3-100%）
- 所有配置（除Expand外）均达到100% HR@3，因问题关键词与文档术语完全匹配
- Expand 模式降至83.3%，因为拆解出的子问题引入了无关噪声
- **结论**: 对事实性查询，基础检索已足够，无需额外增强

#### B类-口语化/术语转换（HR@3 = 83.3-100%）
- BM25 弱于 Vector 和 Hybrid（83.3% vs 100%），因口语化用词与文档关键词不重叠
- Rewrite 将 B 类题的 Hybrid HR@3 从 83.3% 提升至 100%，说明口语→术语改写有效
- **结论**: Query Rewriting 的主要收益场景是B类题

#### C类-条件排除性查询（HR@3 = 100%）
- 所有配置均完美命中，因条件相关关键词（"不及格""开除"等）在文档中明确出现
- **结论**: 当前系统对此类问题已无优化空间

#### D类-跨文档关联（HR@3 = 66.7% — 系统最大瓶颈）
- **所有7种配置均相同得分**，说明这不是某个组件的问题，而是**架构性局限**
- 6道题中有2道（五四奖章+奖学金共同条件、新旧政策对比）始终无法同时检索到两个相关文档
- 根因：当前系统是单文档检索，每次只从一个文档集合中返回 Top-K
- D类题中 Q22（五四奖章评选与奖学金评选的共同条件）在 LLM-as-Judge 中得分最低（F=3, R=3-4, C=2），因为检索只找到一份文档
- **解决方案方向**: 多跳检索（Multi-hop Retrieval）或知识图谱（GraphRAG），见后续规划

#### E类-复杂多维度（HR@3 = 100%, Expand 83.3%）
- 单文档内的复杂问题（如"保研需要什么条件"）各配置处理良好
- Expand 再次表现不佳（83.3%），与A类观察一致
- **结论**: Expand 在当前场景下弊大于利

### 6.2 关键发现总结

1. **建议默认配置: Hybrid仅此而已**。添加更多组件并未带来实质性收益
2. **Query Rewrite 有边际收益**：Precision@3 +3.4%，主要受益在B类口语化问题
3. **Multi-Query Expand 不推荐**：除E类题外全面下降，引入噪声 > 提升召回
4. **Reranker 未达预期**：基线已高（HR@3=93%），无优化空间；且切断候选集损失了正确结果
5. **跨文档问题是架构性瓶颈**：所有配置均66.7%，需要 GraphRAG 级别解决
6. **生成质量普遍优秀**：Overall 4.6-4.9/5，说明 RAG 管道整体可靠

## 七、错误案例分析

### Case 1: 跨文档关联失败（D类 Q22）
- **问题**: "五四奖章评选与奖学金评选有什么共同条件？"
- **期望**: 从五四奖章通知中提取"热爱祖国/拥护党的领导"等条件，同时从奖学金办法中提取相同条件，找交集
- **失败表现**: 检索只命中了奖学金文档或五四奖章文档之一，无法获取完整信息
- **根因**: 单文档检索架构无法同时精确命中两个跨主题文档
- **建议**: 实现多跳检索：先检索第一个文档获取信息，再用该信息构造第二个查询

### Case 2: Expand 噪声引入（A类 B类部分题目）
- **问题**: "一等奖学金的金额是多少？" → Expand 拆解为"奖学金等级有哪些？" "一等金额多少？" "评选标准是什么？" → 后两个子问题检索结果不精准，RRF 融合后反而稀释了正确答案的排名
- **根因**: Expand prompt 设计的拆解粒度与检索需求不匹配
- **建议**: 优化 Expand prompt，限制子问题数量（目前最多6个），或增加相关性过滤

### Case 3: 生成完整性不足（E类 Q27）
- **问题**: "考试作弊的完整处理流程" → Vector 模式 Completeness=3/5
- **表现**: 回答提到了主要步骤但遗漏了部分细节（如申诉时限10天、材料归档要求）
- **根因**: Top-3检索片段可能切断了关键的程序性信息（chunk_size=300 偏小）
- **建议**: ①尝试增大 chunk_size 至 500；②切片策略改为按章节语义切片而非固定字符数

## 十二、系统有效性分析：RAG是否真正解决了问题？

### 12.1 它能做什么（有效场景）

**场景1：学生查询奖学金/保研的具体规定**
- 如"一等奖学金多少钱？""保研GPA要多少？"→ 秒回，准确率100%
- 这是系统的核心价值场景：替代人工翻阅30+页PDF

**场景2：学生用口语/大白话问政策**
- 如"被处分了还能拿奖学金吗？"→ 自动理解意图，准确回答
- 相比传统关键词搜索（如百度站内搜），RAG的语义理解优势在此体现

**场景3：需要排除条款的问题**
- 如"有不及格课程能否保研？"→ 系统能同时理解"保研条件"和"排除条件"两个维度

**场景4：多条件综合查询（单文档内）**
- 如"奖学金有几等？金额比例各是多少？"→ 从同一文档的多个片段中整合信息

### 12.2 它不能做什么（失效场景）

**场景1：需要跨两份文档推理**
- 如"五四奖章和奖学金评选的共同条件是什么？"
- 系统通常只找到其中一份文档，无法做交集推理
- **现实意义**: 学生如果问"我考试作弊了，还能保研吗？"可能需要交叉引用违纪办法和保研细则——系统会漏掉部分信息

**场景2：对比新旧政策差异**
- 如"2025版违纪细则相比2017版有哪些变化？"
- 系统无法自动识别两版文档的差异并做diff分析
- **现实意义**: 政策更新时，学生最关心的就是"和以前有什么不一样"，系统目前做不到

**场景3：涉及"未明确提及"的推断**
- 如"被开除学籍后奖学金要退吗？"→ 文档中未提及
- 系统可能强行给出错误答案，而不是诚实地说"文档中未提及"
- **现实意义**: 对未知信息的判断力不足，可能在灰色地带给出误导性答案

**场景4：长流程/程序性查询（生成完整性不足）**
- 如"考试作弊的处理流程是什么？"→ 答案可能漏掉申诉时限、材料归档等细节
- **现实意义**: 学生按不完整的流程操作，可能错过申诉窗口

### 12.3 综合评级

| 评估维度 | 评分 | 说明 |
|---------|------|------|
| **回答准确性** | ⭐⭐⭐⭐⭐ | 找到正确文档后，回答几乎完全正确 |
| **响应速度** | ⭐⭐⭐⭐⭐ | 基础配置0.02s/题，可支撑实时交互 |
| **口语理解** | ⭐⭐⭐⭐ | Hybrid+Rewrite覆盖大部分口语化场景 |
| **复杂推理** | ⭐⭐⭐ | 单文档内多条件查询OK，跨文档能力弱 |
| **完整性** | ⭐⭐⭐⭐ | 多数回答完整，长流程偶有遗漏 |
| **诚实性（拒答）** | ⭐⭐ | 对无答案问题倾向"硬答"而非拒绝 |
| **政策对比能力** | ⭐⭐ | 不支持diff式对比 |
| **综合实用度** | ⭐⭐⭐⭐ | 对**单文档事实查询**场景已具备生产可用性 |

### 12.4 一句话总结

> **能解决80%的问题，但20%的关键难题仍需改进。**

具体来说：
- **可以上线的场景**: 奖学金/保研/违纪的单项政策咨询。学生问"XX条件是什么"，系统秒回且可靠
- **需要人工兜底的场景**: 跨文档问题（如处分对保研的影响）、政策对比、程序性长流程。建议在UI上标注"仅供参考，请以官方文件为准"
- **不推荐的场景**: 需要法律级别准确性的政策裁决、新旧版政策自动diff分析

### 12.5 对产品化的建议

1. **MVP上线配置**: Hybrid检索即可（配置③），准确率高且延迟低
2. **UI提示优化**: 对跨文档问题展示"以下回答仅基于单份文档，建议查阅相关文件"
3. **渐进式改进**: 优先实现多跳检索（最简单的跨文档方案），再考虑GraphRAG
4. **安全机制**: 添加"文档未提及"检测，避免模型在无答案时胡乱臆测
5. **落地价值**: 对东北大学学工部/教务处而言，该系统可将常见政策咨询的响应效率从"2-3个工作日（人工翻文件）"提升至"实时回复"，尤其适合集成到企业微信或公众号作为智能客服
